## 1. 条件聚合还需声明承诺日期已通过质量检查

位置为 `read-03-0089`、`read-03-0090` 及紧接的 SQL。

SQL 仅过滤 `actual_date IS NOT NULL`，却直接将 `actual_date <= promised_date` 不为真的记录归为 `on_time_flag=0`。若实际日期有值而承诺日期缺失，这个条件得到未知，仍进入 `ELSE 0`，从而被解释为延期。新稿已经系统说明空值与失败状态不同，此处还需给出适用前提。日期差计算在不同数据库对空值的具体处理也有差异。

建议在代码说明中明确，此样例要求承诺日期非空、有效且与实际日期采用一致的时间含义；承诺日期不明的记录应列为待核查，不能凭 `ELSE 0` 判定延期。原样例数据满足此条件，代码可保留。配套 Python 的 `enrich_orders()` 已在承诺日期缺失时抛出错误，说明两种实现的输入条件也应保持一致。

## 2. 配套 SQL 的客户窗口仍只包含已交付订单

位置为 `read-03-0198`，并关联 `read-03-0183` 与 `read-03-0192`。

正文展示的客户窗口查询直接读取全部订单，Python 的 `rolling_customer_revenue()` 也在全部订单中取最近三笔；配套 `build_kpi_tables.sql` 的 `customer_order_window` 却读取已由 `WHERE actual_date IS NOT NULL` 过滤的 `order_enriched`。这项差异不只改变销售额，还会改变某笔订单的前两笔究竟是谁。当前干净样例全部已交付，因此不会暴露该差别。

建议在配套脚本段落明确其窗口是“最近三笔已交付订单”，并与正文“最近三笔订单”分开命名；独立复算时既要选择相同订单集合，也要在该集合上重新建立排序与窗口。若选择修改代码，则需同步本轮程序源与实验测试，本次可通过清楚说明限定范围避免扩大修改。

## 3. WIP 各产品族相加需限定同一快照时点

位置为 `read-03-0086` 最后一句。

当前说法为“同日按互不重叠的产品族分别记录在制品”，随后要求求出每天工站总量。“同日”不足以保证时点存量可相加，例如上午的甲产品族与下午的乙产品族快照，不共同构成某一时点的工站总在制品。

建议改为同一工站、同一快照时点或统一日结时刻、且产品族范围互不重叠时求和；再按规定的时间权重计算期间均值。这样与本节先定义的时点存量完全一致。
