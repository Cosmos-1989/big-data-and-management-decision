# 企业 Agent 教学实验独立核查

日期：2026-10-12。范围：`src/bdm_decision/cases/week14_enterprise_agents.py`、四项交互实验的 `experiments.json`、`cases.md` 及原有 `test_agent_cases.py`。本轮先独立注入反例，再按根代理授权修复教学 Python 模块和案例规范；没有修改网站构建、应用界面或其他章节。

## 结论

首次独立检查 144 项，135 项通过，发现 9 项失败，归为两类阻断：未经核对的事件缓存复用，以及非布尔输入导致身份或联锁判断失真。现已修复这些问题并增加审批/版本反例；内容复审又提出地区适用范围及不必要政策审批入口的风险，均已同步处理。最终独立检查 **159/159**，15 组全部通过；原标准样本与交互片段仍为 **48/48**。当前没有未解决的实验规则阻断。此结果仅证明确定性教学规则在这些输入下满足所检性质，不证明真实企业 Agent 的业务效果、认证安全性或设备安全性。

可执行检查：

```sh
python3 /private/tmp/bdm-agent-extension/test_agent_cases.py
python3 /private/tmp/bdm-agent-extension/independent_lab_checks.py
```

逐项输入标签、实际输出和通过状态保存于 `independent-lab-results.json`。该文件同时保存被测模块的 SHA-256，便于识别后续代码是否变化。检查脚本只写入自身 JSON 结果文件；不调用网络或企业系统，不修改生产数据。测试过程中的资料、日历及阈值反例在 `finally` 中恢复。

## 原阻断及修复

| 原反例 | 首次实际结果 | 修复后的要求与结果 |
|---|---|---|
| U1 已核验查询 O100，U2 使用同一事件号查询 O100 | 回放“已发货”，泄露另一客户订单状态 | 以任务、调用身份、事件号共同隔离；U2 重新核验订单归属，得到 `privacy_block`，无可见事实 |
| 已回复物流的事件同号改为“设备冒烟和物流” | 回放普通订单答复，遗漏新安全证据 | 请求指纹不同，返回 `event_conflict`，不回放旧订单状态；更新咨询须使用新事件号 |
| 先记录正常产线事件，同号再上报 `interlock_trip=True` | 回放 `monitor/closed` | 返回 `event_conflict`，禁止沿用旧“正常”结果；同时明确交现场值班工程师处理当前联锁上报，控制调用为零 |
| 会议与产线共享同一账本及事件号 | 产线读到会议提案结构，联锁未处理 | 任务键隔离；产线返回 `interlock_escalate`，不会读取会议结果 |
| 客服 `verified='false'` | Python 真值使订单状态可见 | 严格布尔校验，返回 `invalid_input`，不显示订单事实 |
| 会议 `organizer_authenticated='false'` | 真值使会议成为 `committed` | 仅真正的 `True` 可通过；返回拒绝，不返回已批准状态 |
| `interlock_trip=1/'true'/None` | 均被当作未联锁并返回正常 | 必须为布尔值，否则 `invalid_input`；风险分数为空，设备指令为零 |

账本保存完整请求、规则版本、请求指纹、当前结果与结果指纹。只有完整请求一致才能回放。审批函数推进已保存提案的结果，不改写原请求；返回字典的修改不会篡改账本。它还会检查当前规则和业务资料版本，禁止在阈值、日历或订单资料变化后使用旧提案或旧事实。

会议审批绑定组织者、事件、参与人、时段、日历版本、请求指纹与审批标识。标准 `ORG-1` 在同一账本中只能批准首次绑定的提案，不得用于第二个事件；已批准会议再次审批也重新核验身份和标识。产线工单再次审批仍检查维护负责人角色；不合格审批不回放旧批准工单。制度问答不提供经理审批函数；原不必要的 `approve_policy` 已删除，避免将自报经理身份或伪造证据当作合法批准。问答只输出待经理预审，由实际企业流程完成。

## 独立检查覆盖

1. 住宿制度切换日、自动额度和经理预审上限：350/350.01/500/500.01、400/400.01/600/600.01；发票 30/31 日边界。
2. 无权限、无有效期、无地区条款、多意图、薪资限制、最高版本冲突。拒答输出不包含受限条款正文。
3. 研发资料须同时已批准且角色可读；草稿 v2 不替代已批准 v1；相同最高版本冲突不输出事实。
4. 会议集合交集、无共同空档、审批错参与人/时段/事件号、无身份核验及正确本地审批。
5. 工单完全相同请求回放，新增工单数为零；修改返回字典不影响账本。
6. 客服安全优先于退款、订单、产品，退款优先于订单和产品；14/15 日退款入口边界，均不执行支付。
7. 产线 72 种组合：振动 7.9/8.0/8.1、温度 79/80/81、质量 good/bad、年龄 60/61、联锁 false/true。阈值等号计异常，年龄 61 不判正常，联锁为真时优先人工处理。所有组合的设备指令及未经授权新增工单均为零。
8. 缺失、NaN、无穷值、负年龄、布尔年龄、未知设备、未知质量、缺失批次、未来时间及未经规范化的时区时间戳。
9. 客户身份改变、已核验资格撤销、同号新安全消息、同号新联锁、跨任务事件碰撞。
10. 严格布尔：客户核验、组织者核验、PLC 联锁及产品批准标志，字符串不按真值通过。
11. 会议审批标识重复用于另一事件、同号改参与人、已批准会议撤销核验、已批准工单错角色重交。
12. 日历、订单资料和产线阈值变更后，旧证据或旧审批失效。
13. 住宿小数金额与连续预审区间一致；international 发票查询无证据；待经理审批仍为待审；模块不存在直接审批捷径。
14. 四段前端代码中的全部 10 个公开参数，逐个执行其对应赋值变更，确认结果实际改变。客服重试使用真实完整账本，其输出确实为 `replayed=True`。
15. 四项实验独立重复运行得到相同显示结果，确定性边界明确。

## 代码、前端与案例规范一致性

前端控件通过 `lab.js` 的赋值替换更新可见 Python 代码；四段片段均有对应的顶层赋值，实际执行证明结果变化，未发现伪交互。首次载入仍需要课程静态资源可用；“完全离线”只可用于模块本身的 Python 复算，不能理解为首次打开网页不需要资源。

代码只导入标准库，四个模块没有语言模型推理、企业 API、日历提交、退款支付或设备停启/复位/调参调用。PLC 状态是只读的教学输入，`control_commands` 始终为空。教学身份/审批开关是显式输入，不是真实认证；指纹用于检测同次模拟输入变化，不赋予企业权限。

已同步 `cases.md` 的以下偏差：小数金额的预审区间、住宿和发票地区均限定 domestic、制度冲突返回 `conflict_review`、会议实际输出字段、同版本研发冲突条件、`matched_keywords` 实际保存的是意图标签、严格幂等规范、非布尔联锁处理，以及原型只记录最终状态而未实现完整工单关闭/拒绝落库流程。案例把完整企业流程蓝图与当前确定性原型区分开，避免声称已经实现真实多 Agent 或完整业务系统。

原 40 组标准样本的重复事件使用的载荷相同，因此无需修改其期望。网站客服片段原先手造 `ledger={'CASE-1': result}`，由根代理改为首次调用及重试共同使用正式账本；独立执行已验证这个改动。

## 可改进项（非阻断）

- 可在结果表中增加条款摘录、生效区间、规则版本及请求指纹，便于学生核查完整证据链；当前默认显示较精简。
- 可增加标准样本载入器和字段表单，直接覆盖 40 组课堂样本；目前部分失败分支需要编辑 Python 参数或运行检查脚本。
- 可将实际命中词另设 `matched_words`，同时保留意图标签；当前 `matched_keywords` 命名容易让学生误以为是原词列表。
- 完整审批拒绝、撤销、审计时间、人工改路由及正式工单关闭属于后续流程扩展。本轮已删去“原型具备全部状态轨迹”的不实描述。
- 真正的企业接入需要凭证认证、服务端权限校验、不可篡改持久日志、数据库级幂等、设备数据来源认证和生产场景评价；本模拟不提供这些保证，不能把课堂通过率当作上线验收率。
