# 企业 AI Agent 教学案例包

本案例包使用完全虚构的企业、人员、文件、订单和设备记录。金额、时限、指标阈值与审批规则仅是可复算的课堂参数，不代表法律要求、真实企业制度或设备控制规范。四个前端实验均使用本地固定数据、关键词词典、规则路由与状态机；它们模拟 Agent 的任务分解和控制流程，**不调用语言模型，也不声称具备自然语言理解、真实企业系统权限或自动执行能力**。学生可修改结构化输入，观察可解释的检索、决策与失败分支。

## 共同任务框架

企业流程可按 `输入 → 数据与权限核验 → 证据/规则匹配 → 候选输出 → 独立校验 → 人工审批 → 状态确认 → 审计记录` 设计。本模拟实现规则判定、必要的权限与证据筛选、本地提案审批及内存账本；输出使用 `decision` 或 `route` 表示判定，并给出 `reason`、`state`，适用时补充证据和下一处理人。证据不足时保留“无法确定”，不得补写事实。账本以“任务类型、调用身份、事件号”共同定位，保存规则版本、完整请求与结果的指纹，以及当前结果。只有相同请求才能回放；同号载荷、核验状态、资料或规则版本改变返回 `event_conflict`，不输出旧敏感事实或旧批准结果。不同任务与不同身份的账本范围隔离。审批函数在核验原提案、当前版本与审核资格后推进状态；同一会议审批标识不能绑定第二个事件。所有核验标志和联锁状态必须为真正的布尔值，字符串 `"false"`、数字 `1` 不代表通过核验。前端的“审批”“提交”只改变本地演示状态，不写入外部业务系统。

在教学实现中，**Skill** 是有输入模式、输出模式、适用范围和失败条件的可复用任务配方，例如“核对政策版本”“审计引用”“计算可用会议时段”“按优先级分流”“核验设备事件”；它不等于授权。**Harness** 管理任务状态、超时、权限、工具允许列表、证据上下文、幂等键、人工审核、审计日志及终止条件。多个专责 Agent 可以分别提出检索候选、执行计算、审查证据与约束；最终状态由 Harness 和被授权人员决定。本原型用确定性函数代表部分角色，展示输入、命中规则与结果；未实现模型规划、分布式事务、工具超时或真实身份认证。调用身份和审核角色是显式教学参数，指纹用于辨认同次模拟请求，不能替代企业身份凭证。内存账本须由 Harness 管理，学生可编辑代码不意味着能在真实企业系统取得权限。

| 职责 | 可提交的中间结果 | 不能自行完成的事 |
|---|---|---|
| 检索/资料 Agent | 有版本、有效期、权限标签的候选证据 | 改写制度原文或绕过文档权限 |
| 业务分析 Agent | 结构化计算、规则命中、候选解释 | 将无证据猜测写成企业结论 |
| 核查 Agent | 来源核对、冲突/缺失、口径与权限检查 | 代替制度负责人、客服或设备负责人批准 |
| Harness | 排序、调用、状态转移、重试/终止、留痕 | 创造权限、替代 PLC 联锁或取消人工复核 |

课程可按五阶段推进：**原型**用教学数据固定输入与标准答案；**沙盒验证**加入缺失、冲突、越权、超时、重复提交等故障样本并全量复测；**灰度试点**先只读、再对少量低风险任务启用带审批的建议，预先指定责任人和对照指标；**回滚**在错答、越权、漏告警或审计缺失达到停用阈值时停止新任务、保留日志、恢复既有人工流程；**扩展**须重新评估新业务线的数据口径、权限、峰值容量和责任边界。案例中列出的试点验收阈值是教学设定，真实项目须由业务与安全负责人制定。

| 阶段 | 可做的事 | 进入下一阶段的门槛 |
|---|---|---|
| 原型 | 固定教学数据、结构化输入、确定性规则 | 本文件标准样本全部通过，输出可逐步解释 |
| 沙盒 | 加入越权、重复、缺失、冲突和超时事件 | 高风险误放行、无审批执行和审计缺失均为零 |
| 灰度试点 | 在授权范围内只读或由人工逐项确认建议 | 与既有人工流程并行比较，满足预先登记的准确性和时效阈值 |
| 回滚 | 停止新自动任务，保留证据及未完成状态 | 问题复盘、规则/数据修订与独立复测完成后才可重启 |
| 扩展 | 逐业务线、逐角色增加范围 | 新范围的权限、数据口径、容量和责任人重新审批 |

## 案例一：企业制度可信问答

### 背景与任务

虚构企业“澄川制造”的员工出差前常询问住宿额度、发票提交期限。旧版与新版制度同时存档；直接用关键词命中第一份文档，可能引用失效条款。实验目标是：对一个结构化问题，先核验询问者权限与业务日期，再选择当时有效的制度，输出可核对的结论和条款编号。问题若没有有效证据，返回澄清或转交制度负责人。

### 教学数据、对象与输入

| 文档 ID | 生效区间 | 访问范围 | 条款与规则 |
|---|---|---|---|
| `HOTEL-v2` | 2026-01-01 至 2026-09-30 | 全体员工 | 国内住宿每晚 `≤350` 元可按制度报销；`350<金额≤500` 元须在预订前经部门经理批准；`>500` 元不在本条款支持范围。 |
| `HOTEL-v3` | 2026-10-01 起 | 全体员工 | 国内住宿每晚 `≤400` 元可按制度报销；`400<金额≤600` 元须在预订前经部门经理批准；`>600` 元不在本条款支持范围。 |
| `INVOICE-v1` | 2026-01-01 起 | 全体员工 | 教学设定：出差结束后 `30` 个自然日内提交合规发票。 |
| `PAYROLL-v1` | 2026-01-01 起 | 人力资源受限库 | 薪资明细由受控 HR 系统处理；本实验不检索、展示或推断个人薪资。 |

输入为 `{question, role, as_of, region, amount_yuan?, days_after_trip?}`。关键词词典只识别“住宿/酒店”“发票”“工资/薪资”三种意图；同时出现两个意图返回 `clarify`。`as_of` 用于选制度版本，本实验的住宿和发票条款均仅适用于 `domestic`；其他地区返回无证据。金额和天数必须是非负数，缺少关键字段先请求补充。姓名、账号与私人票据内容不进入教学数据。

### 规则、输出与失败分支

1. 解析固定关键词；无法唯一归类时返回 `clarify`，不生成答案。
2. 对非敏感意图，以 `as_of` 过滤有效制度，再按最高版本号选择。只有标题匹配、却已失效的文档不得引用。
3. `hotel` 按当期额度返回 `eligible`、`manager_preapproval` 或 `outside_policy`；后两种均不得写成已经批准或已经报销。
4. `invoice` 在 `days_after_trip≤30` 时返回 `within_window`，否则返回 `late_review`，提示人工检查例外规则；不自动拒付。
5. 薪资意图始终返回 `restricted_transfer`，不检索受限正文，不显示个人数值。证据库缺失或地区不符时返回 `no_evidence`；同一最高版本存在多份有效候选时返回 `conflict_review`，由制度负责人复核。

输出 `{decision, evidence_ids, clause_summary, reason, next_actor, state}`。`answer_policy` 的 `state` 为 `answered`、`pending_review`、`clarify` 或 `restricted`。本问答实验不提供经理审批函数，只指出需要预先审批，由企业实际流程完成。界面必须把制度原文摘录、版本/有效期和系统按规则作出的判断分开显示。员工自行点击“确认”不构成经理预审；模型答复及调用者自报的经理身份均不构成批准。

**可手算示例。** 员工在 `2026-10-10` 查询国内住宿 `450` 元/晚。`HOTEL-v2` 已失效，`HOTEL-v3` 的自动范围到 `400`，预审范围到 `600`，因此结果是 `manager_preapproval`、证据 `HOTEL-v3`、下一处理人“部门经理”，状态 `pending_review`。直接引用旧版或回答“可直接报销”均不合格。

### 前端实验与标准输入输出

前端按关键词映射意图，按日期筛文档，按阈值运算。下表中 `role=employee`、`region=domestic`，未列字段沿用当行意图所需的有效默认值。期望输出写核心判定与证据；实际 UI 还需显示原因及下一处理人。

| # | 输入（教学 JSON 的关键字段） | 期望结果 |
|---:|---|---|
| 1 | `住宿; as_of=2026-10-10; amount_yuan=380` | `eligible; HOTEL-v3; answered` |
| 2 | `酒店; 2026-10-10; 450` | `manager_preapproval; HOTEL-v3; pending_review` |
| 3 | `住宿; 2026-10-10; 700` | `outside_policy; HOTEL-v3; pending_review` |
| 4 | `住宿; 2026-09-15; 380` | `manager_preapproval; HOTEL-v2; pending_review` |
| 5 | `发票; 2026-10-10; days_after_trip=20` | `within_window; INVOICE-v1; answered` |
| 6 | `发票; 2026-10-10; days_after_trip=45` | `late_review; INVOICE-v1; pending_review` |
| 7 | `工资; 2026-10-10; role=employee` | `restricted_transfer; 无引用正文; restricted` |
| 8 | `住宿; 2026-10-10; region=international; 380` | `no_evidence; 无有效文档; clarify` |
| 9 | `发票和酒店; 2026-10-10` | `clarify; 意图不唯一; clarify` |

验收：九组标准样本判定及版本引用全对；越权泄露次数为零；每个肯定答复有有效条款和时间边界；失败分支不给出编造的额度。沙盒再加同日起生效的冲突文件，预期停止自动答复并交制度负责人复核。

## 案例二：办公数字员工与研发助手

### 背景与任务

同一企业希望减轻会议排期和研发资料检索的重复工作。办公任务需要计算共同空档，但不能在未经会议组织者确认时替其发送邀请。研发任务需要根据主题找已批准且在当前权限范围内的版本，不能把过期资料或未发布设计稿当作定论。两个任务共享 Harness 的身份、权限、证据、审批和日志机制，但有不同 Skill 与完成条件。

### 教学数据、对象与输入

会议只考虑虚构的 `2026-10-13` 三个半小时槽位：`S1=09:00`、`S2=10:00`、`S3=14:00`。参与人“李”可用 `{S1,S2}`，“王”可用 `{S2,S3}`，“赵”可用 `{S1,S3}`。若多个共同空档，选时间最早者；三人均需参会时没有共同空档。没有真实日历连接。

研发资料库：`R-VIB-v1`（泵振动故障旧版，已被替代）、`R-VIB-v2`（已批准的振动排查卡，员工可读，结论为“先核对传感器校准与轴承检查记录”）、`R-CHIP-v1`（已批准的芯片接口设计约束，仅 `engineer` 可读，结论为“接口额定电压 3.3 V”）、`R-CHIP-draft`（草稿，任何角色都不可作为正式答复证据）。研究问题只识别“泵振动”和“芯片接口”关键词。文档正文均为教学虚构内容。

输入采用两种互斥模式：

- 排期：`{task:"meeting", event_id, organizer_id?, participants:[...], organizer_authenticated, approval_id?}`；参与人只能为“李/王/赵”，`approval_id` 必须由组织者在模拟审批控件产生；标准审批标识 `ORG-1` 只允许“李+王、S2”，并在同一账本中绑定首次批准的事件号与请求指纹，不能复用于另一事件。一般教学审批标识 `APPROVE:事件号:时段` 也须匹配该组织者的原提案与当前日历版本。
- 研发：`{task:"research", topic, role}`；`role` 为 `employee` 或 `engineer`，查询只能返回当前已批准且允许该角色阅读的最新版。

### 规则、输出与失败分支

排期 Skill 求参与人空档交集并取最早一项，输出 `{decision, proposal_slot, state, next_actor, reason}`。有共同空档时先是 `proposed`；只有 `organizer_authenticated=true` 且存在匹配的 `approval_id`，才转为本地演示的 `committed`。没有交集时 `conflict`，建议人工改期，不自动移走他人会议。相同任务、组织者、事件号和完整请求返回已有结果，不重复提交；同号改参与人或日历版本则返回 `event_conflict`，须建立新事件并重新审核。已批准提案被重复审批时仍核验组织者与审批标识，不能绕过检查。

研发 Skill 先过滤权限与 `status=approved`，再以主题关键词确定候选，选择最新非废止版本。输出 `{answer_fact, evidence_ids, state}`。无匹配为 `no_evidence`；只有受限文件为 `access_denied`，不透露正文；同一最高可见版本存在多份已批准候选时为 `conflict_review`；正常并存的历史低版本由版本选择规则处理。任何改代码、合并补丁或提交研发结论的动作都不在此模拟范围内。

**可手算示例。** “李”和“赵”的共同空档是 `{S1,S2}∩{S1,S3}={S1}`，故推荐 `09:00`。未提供组织者审批时状态只能是 `proposed`。查询“泵振动”时，`R-VIB-v1` 已被 `v2` 替代，只能引用 `R-VIB-v2`，给出上述两项核查事实。

### 前端实验与标准输入输出

前端提供“排期”和“研发资料”两个面板：一个做集合交集和状态转移，一个做确定性索引/权限/版本筛选。审批只是本地状态，任何按钮都不发送真实邀请。

| # | 输入 | 期望结果 |
|---:|---|---|
| 1 | `meeting; participants=[李,王]; 无审批` | `S2=10:00; proposed` |
| 2 | `meeting; [李,赵]; 无审批` | `S1=09:00; proposed` |
| 3 | `meeting; [王,赵]; 无审批` | `S3=14:00; proposed` |
| 4 | `meeting; [李,王,赵]; 无审批` | `无共同空档; conflict` |
| 5 | `meeting; [李,王]; organizer_authenticated=true; approval_id=ORG-1` | `S2=10:00; committed（仅本地）` |
| 6 | `research; topic=泵振动; role=employee` | `引用 R-VIB-v2；核对传感器校准与轴承检查记录` |
| 7 | `research; topic=芯片接口; role=employee` | `access_denied；不显示 R-CHIP-v1 正文` |
| 8 | `research; topic=芯片接口; role=engineer` | `引用 R-CHIP-v1；额定电压 3.3 V` |
| 9 | `research; topic=未知电路; role=engineer` | `no_evidence；请人工补充资料` |

验收：空档计算、版本选择和权限处理九组全对；无审批“提交”次数为零；过期资料引用和草稿引用均为零；每条研发事实都有文档 ID。灰度前先记录人工排期耗时、冲突修改次数、资料检索正确率，并与人工流程对照。

## 案例三：客户咨询分流工作流

### 背景与任务

虚构客服中心同时收到订单进度、退货、产品规格及安全相关消息。目标不是让一个对话模型自行答复所有问题，而是让系统先作可解释的优先级分流，在权限和制度允许范围内给出事实，并将需要判断或执行的请求送给人工客服。

### 教学数据、对象与输入

订单 `O100` 属于客户 `U1`、状态“已发货”；`O101` 属于 `U2`、状态“待发货”。产品资料 `P1` 已批准，额定功率 `500 W`。教学退货规则：购买后 `≤14` 日且商品未开封，可进入人工退货审核；其余进入人工例外复核，系统不直接退款或拒付。该 `14` 日仅是案例假设。消息关键词及优先级：`受伤/冒烟`（安全） > `退款/退货` > `物流/订单` > `规格/功率`。一个消息触发多类时只走最高优先级，并保存全部命中意图类别；输出字段 `matched_keywords` 在此教学接口中存放意图标签（如 `safety`、`order`），而不是原始命中词。

输入 `{event_id, customer_id, verified, message, order_id?, days_since_purchase?, unopened?, product_id?}`。`verified` 是身份已核验标志；单有订单编号不足以查看订单。若关键字段缺失，回复补充信息或转人工，不猜订单状态。`verified` 必须为布尔值；其他类型返回 `invalid_input`。

### 规则、输出与失败分支

1. 安全词命中则 `safety_escalate`，立即交人工安全/客服值班组，显示“停止使用并联系人工”的**通用提示**；不进行技术诊断、不引导顾客自行拆修。该优先级高于订单或退款。
2. 退货意图先核验客户；未核验为 `verify_identity`。核验通过且 `days≤14`、`unopened=true` 时为 `refund_review`；其他情况为 `exception_review`。两者均需客服批准，模拟器不支付款项。
3. 订单意图须同时满足 `verified=true` 和订单归属匹配，才可输出状态；归属不符为 `privacy_block`，不展示状态。
4. 产品规格意图只引用已批准的 `P1` 资料；无对应资料返回 `clarify`。
5. 未知意图返回 `clarify`；相同任务、客户身份、事件号和完整请求读取既有结果；同号改消息、核验标志、订单或资料版本返回 `event_conflict`，不回放旧订单状态。咨询更新应使用新事件号；本模拟不实际创建客服工单。

输出 `{route, visible_fact?, evidence_ids, next_actor, state, matched_keywords}`。可自动回复的事实只有已授权订单状态与已批准产品规格；退款和安全请求的输出是**路由与待处理状态**。人工客服负责确认身份、解释例外、决定退款；安全值班组负责事故处置。

**可手算示例。** 已核验的 `U1` 发“`O100` 的物流怎样”，订单归属匹配，结果为 `order_status`，显示“已发货”。若同一句由 `U2` 发出，即使已核验，也返回 `privacy_block`，不能显示 `O100` 的状态。

## 案例四：生产线异常处理综合方案

### 背景与任务

虚构半导体封测线 `L1` 的工作中心 `M01` 上报振动、温度与批次质量标记。目标是将异常记录转化为可追踪的调查与维护建议，同时保持工业控制系统的独立安全边界。**温度保护和停启机由现场 PLC/安全联锁及有资质人员负责；AI 系统只读取联锁状态，绝不发送停机、开机、复位、参数改写指令。** 教学数据不对应真实设备阈值。

### 教学数据、对象与输入

每条事件 `{event_id, line_id="L1", machine_id="M01", lot_id, vibration_mm_s, temperature_c, sensor_age_s, quality_flag, interlock_trip, approval_by?, observer_id?, event_time?}`。实验阈值：振动 `≥8.0 mm/s` 算异常，温度 `≥80°C` 算异常，`quality_flag="bad"` 算质量异常；传感器读数年龄 `>60 s` 或数值缺失视为不可用于判定。`interlock_trip` 是 PLC 上报的只读布尔状态；非布尔类型返回 `invalid_input`，不能据此判断正常。事件时间使用固定教学时钟 `2026-10-13 18:00` 核验；本例只接受无时区的教学时间戳，带时区输入须先另行规范化，否则进入数据质量复核。本案例**不把 `95°C` 之类阈值伪装成 PLC 的真实联锁设置**。`approval_by="maintenance_lead"` 仅表示在前端模拟中维护负责人批准建工单。所有事件、批次和人员均虚构。

### 规则、状态机与失败分支

先核验事件及联锁字段类型，并检查账本中的任务、观察身份、事件号、请求和规则版本。同号载荷改变返回 `event_conflict`，不回放旧的“正常”结果；若新载荷含当前联锁上报，同时明确转现场值班工程师处理。通过上述检查后，以下业务优先级不可交换：

1. 若 `interlock_trip=true`，输出 `interlock_escalate`、下一处理人“现场值班工程师”、状态 `human_safety_response`；即使传感器数据过期也不能掩盖联锁。系统不发设备控制命令。
2. 否则若传感器缺失、非数值或 `sensor_age_s>60`，输出 `data_quality_hold`，要求核查采集链路；不能因为没有有效数据就判断“正常”。
3. 否则计算教学风险分数 `R = 1[vibration≥8.0] + 1[temperature≥80] + 1[quality_flag=bad]`。`R=0` 为 `monitor`；`R=1` 为 `warning_review`；`R≥2` 为 `high_review`。阈值等号计入异常。
4. `R≥1` 时只生成维护/质量调查工单**草稿**，带原始事件、批次、阈值和命中项；只有维护负责人模拟审批后，状态转 `ticketed_local`。对 `quality_flag=bad` 另给“人工决定是否隔离批次”的建议，系统不自动处置批次。
5. 相同任务、观察身份、事件号及完整请求再提交，返回已有结果与工单 ID，新增工单数为零；同号改设备、批次、读数、联锁或阈值版本返回 `event_conflict`，须核对后建立新事件。出现不识别的设备 ID、缺失批次或未来时间戳时进入 `data_quality_hold`。审批角色不符时返回 `approval_denied`，既不新建工单，也不返回旧批准状态。

企业完整流程可设计为 `observed → validated → triaged → proposed → reviewed → ticketed_local → closed`。本模拟直接返回规则判定后的状态：正常为 `closed`，数据不合格为 `data_quality_hold`，异常草稿为 `proposed`，经维护负责人模拟审批为 `ticketed_local`，联锁事件为 `human_safety_response`。审批不合格返回 `approval_denied` 与原因，不修改已保存工单；尚未实现正式工单关闭、审核拒绝落库及完整生产流程状态轨迹。输出 `{route, risk_score?, matched_signals, evidence_event_id, proposed_action, next_actor, state, ticket_id?}`。独立的安全系统决定设备状态；维护负责人决定工单，质量负责人决定批次处置，生产负责人协调产能和交付。模型建议不构成上述批准。

**可手算示例。** 事件 `E01`：振动 `8.0`、温度 `82`、质量 `bad`、年龄 `20 s`、联锁未触发。三项均命中，`R=3`，所以输出 `high_review` 和待审批调查草稿；没有维护负责人审批时不存在正式工单。若同一事件后来被重复上报，结果复用 `E01` 的记录，不再建草稿。

### 前端实验与标准输入输出

前端提供振动滑块、读数过期和联锁开关、阈值命中解释、最终状态与本地审批模拟；完整事件字段可在代码编辑区修改。它没有实现真实设备接入或完整工单状态轨迹。规则函数可完全离线复算；展示“PLC 联锁状态：只读”及“设备控制调用数：0”。下表未列时默认 `L1/M01`、`sensor_age_s=20`、`quality_flag=good`、`interlock_trip=false`、未审批。

| # | 输入 | 期望结果 |
|---:|---|---|
| 1 | `E01; vibration=7.9; temperature=79` | `R=0; monitor; closed` |
| 2 | `E02; vibration=8.0; temperature=79` | `R=1; warning_review; proposed` |
| 3 | `E03; vibration=7.9; temperature=80` | `R=1; warning_review; proposed` |
| 4 | `E04; vibration=8.2; temperature=81` | `R=2; high_review; proposed` |
| 5 | `E05; vibration=7.0; temperature=75; quality_flag=bad` | `R=1; warning_review; 另建议质量负责人核查批次` |
| 6 | `E06; vibration=7.0; temperature=75; sensor_age_s=61` | `data_quality_hold; 不给正常判定` |
| 7 | `E07; vibration=7.0; temperature=75; interlock_trip=true` | `interlock_escalate; human_safety_response; 控制调用 0` |
| 8 | `E07` 再次提交完全相同记录 | `返回原事件与状态；新工单数 0` |
| 9 | `E08; vibration=8.0; temperature=79; approval_by=maintenance_lead` | `R=1; ticketed_local; 仅创建本地模拟工单` |
| 10 | `E09; vibration=7.0; temperature 缺失` | `data_quality_hold; 不计算 R` |

验收：十二组分支、阈值边界和优先级全对；联锁漏升级、自动停启/复位命令、无审批正式工单、重复工单均为零；内存账本中的每个异常记录可回溯到请求中的事件、批次、传感器年龄、阈值及规则版本；批准结果保存模拟审核角色。沙盒须注入传感器失联、完全相同的重复事件、同号变载荷、联锁与质量异常同时出现、无权限审批；灰度阶段只能作为只读辅助台，由现场现行流程处置异常。若出现漏告警、权限绕过、无来源建议或工单重复，立即回滚为人工/既有系统流程并复盘，不能由模型自行“修复”联锁逻辑。

## 综合验收与教学提交物

学生应提交四项案例各一份：输入记录、命中规则、证据/引用、输出及状态轨迹、失败分支、人工审批记录、至少一个反例。再提交一张跨案例风险表，区分**资料不可信、权限不符、指标口径错误、状态未确认、设备安全边界**五类失败。最后解释：在哪一步 Skill 可以复用，Harness 如何阻止未授权状态迁移，专责 Agent 的中间结果如何被独立核验，人工为何仍保有最终责任。

课程网站的交互演示宜提供“载入标准样本”“修改输入”“运行”“查看规则轨迹”“重置”五个控件，以及标准答案对照。判定逻辑、教学资料和期望结果作为静态版本化文件随网站发布；规则函数可在 Python 中完全离线复算，网页运行需课程静态资源可用（也可通过本地静态服务器提供）；任何“真实 LLM”“自动退款”“发送日历邀请”“自动停机”字样都不应出现在功能描述中。完成上述标准样本只证明课堂模拟器按规则运行，不证明上线业务效果；生产试点的准确性、时效、成本和风险须在经授权的数据与流程中另行评价。
